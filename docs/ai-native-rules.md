# AI Native 開発ルール（ai-voice-atom 版）

> このプロジェクトで AI エージェント（Claude Code 等）に実装を委譲しながら、**仕様からのドリフト**と
> **検証コスト**を最小化するための運用ルール。汎用ルール（`ai-native-dev-rules.md`）を本リポジトリの
> 現実（ソロ開発・3層構成・submodule 依存・GPU 競合・16k/mono WAV 不変条件）へ落とし込んだもの。
>
> **これは生きたドキュメント。** 同じ誤りを2回踏んだら本書 or `CLAUDE.md` に還元する（[第6章](#第6章--失敗の資産化lessons-learned)）。
> **記憶はヒントであって事実ではない。** ファイル・関数・フラグ名は行動前に実コードで検証する。

---

## 第0章 — 憲法（最上位の3原則）

2026 年のボトルネックはコード生成速度ではなく「仕様からのドリフト」と「検証コスト」。
本プロジェクトの「最強」は次の3つへの投資で決まる。これ以外はすべてこの3つに奉仕する。

1. **Spec（仕様）** — AI が人間に聞かず実装できる、実行可能な仕様。機能追加は必ず Spec から。
2. **Verification（検証）** — AI が人間なしで自己修正できる自動ゲート。緑になるまで「完了」と言わせない。
3. **Isolation（分離）** — 並行作業は所有権を分離。同一ファイルを2体が触らない。

### 破ってはいけない原則

- **仕様なき実装は禁止。** 曖昧な一文をエージェントに渡さない。[第1章](#第1章--spec-駆動)。
- **検証できないものは「完了」ではない。** [品質ゲート](#22-品質ゲートdone-の定義)が全緑で初めて Done。
- **人間は「行」ではなく「決定」を所有する。** アーキテクチャ・受け入れ基準・声色/ペルソナ設計・
  音声フォーマット不変条件の変更可否は人間が握る。実装の自由度は AI へ渡す。
- **失敗は資産化する。** レビュー指摘・バグ・逸脱は Spec か `CLAUDE.md` に還元し、二度と踏ませない。

## 第1章 — Spec 駆動

機能追加は `docs/templates/spec-template.md` から始める。Spec には必ず6要素を入れる
（Outcomes / Scope境界 / Constraints / 既決事項 / タスク分解 / 検証基準）。要件は EARS 形式で
「単一・検証可能な主張」に落とす。

```
ユビキタス:   システムはデバイス向け音声を 16kHz/mono/16-bit PCM WAV で返さなければならない。
状態駆動:     submodule が未初期化である間、host の TTS/STT は機能してはならない（status で configured=false）。
イベント駆動: バックエンドが利用不可のとき、アダプターは RuntimeError を送出しルーターが HTTP 503 を返さなければならない。
```

### このプロジェクトの Constitution（リポジトリ全体に効く絶対要件・EARS）

新規コード・変更は以下に違反してはならない。レビューと self-review はこれを点検する。

- システムはデバイス経路の音声を **16kHz / mono / 16-bit PCM WAV（44 バイトヘッダ）** で出力しなければならない（`utils/wav.py::to_pcm16_mono`）。
- アダプターは「バックエンド利用不可/失敗」に **`RuntimeError`**、不正入力に **`ValueError`** を送出し、ルーターが **HTTP 503 / 400** へマップしなければならない。
- システムは設定を **`AI_VOICE_ATOM_` 接頭辞の環境変数**で受け、**外部の設定ライブラリを追加してはならない**（解析は標準ライブラリのみ）。
- コメント・ユーザー向け文言・ドキュメントは **日本語**でなければならない。
- システムは未登録 `device_id` を**グローバル設定へフォールバック**させなければならない（プロファイル必須化の禁止）。
- ドキュメントとコードが食い違う場合は**コードを正**とする。
- Python コードは **3.11 以上・型ヒント付き**でなければならない。

> **判断**: 小さな修正に重い Spec は不要。`docs/` 仕様や `CLAUDE.md` で十分なら Skill 級で進める。
> 複数層（firmware ↔ host ↔ submodule）をまたぐ変更・API 契約が崩れやすい領域でこそ Spec を厚くする。

## 第2章 — 検証ファースト

### 2.1 自己修正ループが自律の本体

テストが落ちても止まらない。出力を読み、原因を診断し、修正する。この自己修正ループが自律の核心で、
**強いテストがなければ自律は成立しない**。テスト無しのエージェントは過剰な自信で「完了」と言う。

- **バグはテストで再現してから直す。** 修正前に `host/tests/` へ再現テストを書く。
- **フェイク注入で検証する。** 設定/アダプターは import 時固定の実質シングルトン。テストは環境変数ではなく
  **サービスのコンストラクタ経由でフェイクを注入**する（`tests/test_chat.py` の `_FakeOpenAIClient` /
  `_FakeIrodoriAdapter` を範とする）。実 GPU/TTS/STT を起動するテストを書かない。
- **クリティカルパスは手書きで。** 音声フォーマット変換・エラー→HTTP マッピング・履歴分離キー
  （`device_id::session_id`）のテストは AI 任せにせず要件理解の証明として確認する。
- **実機/実音声の検証は `docs/verification-guide.md` の手順**で人間が閉じる（自動化困難な領域）。

### 2.2 品質ゲート（Done の定義）

機能が「完了」と認められる条件。AI はこれを全緑にするまで Done を宣言できない。
コマンドは `host/` から実行（詳細は `/build-test-verify`）。

```
[ ] submodule 初期化済み      git submodule update --init --recursive
[ ] テスト全パス              uv run pytest
[ ] Lint クリーン             uv run ruff check .
[ ] 整形クリーン              uv run ruff format --check .
[ ] 上記の新規テストが存在    変更にひも付く再現/受け入れテストがある
[ ] Constitution 非違反       第1章の EARS 要件を満たす（self-review）
[ ] 実機/実音声の確認         必要なら docs/verification-guide.md を人間が実施
```

> 型チェック（mypy）とカバレッジ閾値は現状ゲート外。導入したら本節へ追記する。

### 2.3 セキュリティは別腹のゲート

LLM 生成物は一定確率で脆弱なコードを含む。本プロジェクトの注意点:

- **外部入力のバリデーション**（WS の `audio.chunk` base64、ヘッダ `device_id`、JSON ボディ）。不正は `ValueError`→400。
- **サブプロセス実行**（`IrodoriTtsAdapter` の `uv run python infer.py`、`tts_server.py`）に
  ユーザー入力を素通しでシェル展開しない。`--caption` 等の引数は配列で渡す。
- **秘密情報をコミットしない**（`.env`、`HOST_BASE_URL`、API キー）。`.env.example` のみ追跡。

## 第3章 — 並行化と分離

ソロ運用でも、独立した機能を並行で進めるとき・同一ファイルを複数体が触りうるときは隔離する。

- **コードを書くサブエージェントは worktree 隔離を既定にする**（`isolation: "worktree"`）。コストはほぼゼロ、衝突が消える。
- 手動の並行は `git worktree add ../atom-feat-x -b feat/x main`。週次で `git worktree list` / `prune` し放置を防ぐ。
- **タスクはファイル所有権が重ならない単位**に切る。例: `host/app/services/` の改修と `frontend/` の改修は分離しやすい。
- **submodule（`third_party/`）の作業状態は共有**。複数 worktree で submodule を同時に書き換えない（`.gitmodules` の固定先を尊重）。
- **GPU は単一資源**。LLM(Ollama) と TTS サイドカーを同時に重く回す検証を並行エージェントで多重起動しない（`docs/performance-tuning.md`）。

## 第4章 — コンテキスト設計（CLAUDE.md）

- **`CLAUDE.md` の各行は人間が承認する。** AI に丸ごと自動生成させない（肥大化は後続全エージェントの認知負荷）。
- **AI が本当に知らないことだけ書く** — 固有のコマンド・固有の規約・固有のアーキテクチャ。一般論（FastAPI とは等）は書かない。
- **ルールは「同じ誤りの2回目」で初めて追加する。** 1回目はまぐれかもしれない。毎回追加すると S/N 比が崩れる。
- 固有制約のあるディレクトリには**ローカル `CLAUDE.md`**（例: `firmware/atom/`）を置いて上書きしてよい。
- 詳細仕様は `docs/`、要約と入口は `CLAUDE.md`。重複させず**ポインタで繋ぐ**。

---

## 第5章 — ガードレールと人間の決定権

- **CLAUDE.md の制約は助言にすぎない。** 実際の強制境界は許可ツールのアロウリスト（`.claude/settings*.json`）だけ。
  破壊的操作・無制限シェルを既定で渡さない。自律ループは隔離 worktree / サンドボックス内で回す。
- **人間が握り続けるもの**: アーキテクチャ、音声フォーマット不変条件・エラー契約の変更可否、ペルソナ/声色設計、
  受け入れ基準（Done の定義）、submodule の更新ポリシー。
- **AI へ渡すもの**: 実装、テスト記述（クリティカル以外）、リファクタ、定型作業、ドキュメント、コミットメッセージ、一次レビュー。

---

## 第6章 — 失敗の資産化（Lessons Learned）

最良の改善源は**レビュー指摘**。「import パターンが違う」→規約へ。「テストコマンドを外した」→
`/build-test-verify` を更新。こうして数週間かけて実挙動を見ながら磨く（初回で完璧を狙わない）。

逸脱・バグ・指摘は `docs/templates/lessons-learned.md` に**絶対日付つき**で追記し、再発防止につなげる。
プロジェクト横断の記憶は Claude Code のメモリ（`MEMORY.md` 索引）にも残す。

## 付録 — 標準フロー

```
1. SPEC      docs/templates/spec-template.md で Spec を起こす（/spec）。人間が確定。
2. PLAN      AI に技術プランを生成させ、人間が承認（主要ゲート）。
3. SPLIT     ファイル所有権が重ならないタスクへ分解。各タスクを SPEC テスト（Scope/Precondition/Expected/Criteria）で検算。
4. ISOLATE   並行なら worktree / サブエージェント隔離。
5. IMPLEMENT AI が実装。再現/受け入れテストを書き、自己修正ループで品質ゲートを緑にする。
6. VERIFY    /build-test-verify が全緑であることを AI が証明。
7. REVIEW    一次レビューを AI（/self-review）。二次を人間（設計・リスク・受け入れ基準）。
8. MERGE     決めたマージ経路で統合。
9. RETRO     指摘・バグ・逸脱を本書 / CLAUDE.md / lessons-learned.md へ還元。worktree を片付ける。
```

> **一枚要約**: 仕様を固め、検証を自動化し、作業を隔離せよ。人間は「決定」を持ち、AI は並行で書き・テストし・自己修正する。
> 速さは所有権から、品質はゲートから、信頼は証明から生まれる。
