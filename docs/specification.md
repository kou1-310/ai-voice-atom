## 1. 目的

AtomS3-Lite と Atomic Echo Base を組み合わせ、OpenAI API 互換の LLM と連携する音声対話デバイスを構築する。

このプロジェクトでは、以下を実現対象とする。

- AtomS3-Lite からネットワーク経由で LLM に問い合わせる
- 応答テキストを AI 音声合成に渡す
- 生成された音声データを受け取り、スピーカーで再生する
- 音声入力（マイク）による音声対話を行う
- ブラウザ UI（ホストが配信）から、実機の会話・話しかけを操作できるようにする
- 複数台に別々のキャラクター（ペルソナ・声色）を割り当てて会話させる
- ホストが無くても単体で遊べるモード（録音再生・オウム返し・タイマー）を持つ

## 2. 方針確認

この方針は妥当である。ただし、初期設計では役割分担を明確にした方がよい。

- AtomS3-Lite はデバイス制御、通信、録音、再生制御のみを担当する
- LLM 推論と音声合成は外部サービスまたは外部ホストで実行する
- OpenAI API 互換のインターフェースを採用し、将来のモデル差し替えを容易にする
- 音声再生フォーマットは初期段階では wav を優先する
- ホスト連携のモード（web / voice / relay）と、ホスト不要のモード（recorder / parrot / timer）を持てる構成にする

AtomS3-Lite は Irodori-TTS や Moonshine を実行しない前提とする。担当範囲は以下に限定する。

- マイク音声の取得
- 音声データまたは制御リクエストの送信
- 応答音声データの受信
- スピーカー再生
- ボタン、LED、効果音による UI 制御

wav を優先する理由は以下の通り。

- ESP32-S3 系では mp4 のデコード実装が初期段階では重くなりやすい
- AtomS3-Lite は 8MB Flash 搭載だが、余裕のあるローカルデコード前提にはしにくい
- Echo Base のスピーカー再生は PCM 系の扱いに寄せた方が検証しやすい
- レイテンシとデバッグ容易性の観点で wav が有利

mp4 を使う場合は、デバイスが直接扱うのではなく、中継サーバーまたはホスト側で wav へ変換してから AtomS3-Lite に渡す構成を推奨する。

また、TTS と STT の採用方針は以下の通りとする。

- テキスト音声合成は Irodori-TTS を採用する
- Irodori-TTS は repo 配下の third_party/irodori-tts を git submodule として管理する
- マイク入力のテキスト化は Moonshine を採用する
- Moonshine は repo 配下の third_party/moonshine を git submodule として管理する
- host の Python 環境構築と実行は uv を標準とする
- Moonshine は低遅延なライブ音声処理向けの STT としてバックエンドまたは中継ホスト上で実行する

## 3. システム構成

### 3.1 構成要素

1. デバイス
   - AtomS3-Lite
   - Atomic Echo Base
2. アプリケーションバックエンド
   - OpenAI API 互換 LLM エンドポイント
   - Irodori-TTS 実行サービス
   - Moonshine STT 実行サービス
   - フロントエンド用ビルド成果物の配信元または同期元
3. 中継レイヤー
   - 認証情報の秘匿
   - 音声フォーマット変換
   - ロギング
   - リトライ制御

### 3.2 操作モード

デバイスは以下の 6 モードを持ち、ボタン長押しで `web → voice → relay → recorder → parrot → timer → web` と巡回する。
選んだモードは不揮発メモリ（NVS）に保存し、次回起動時に復元する。

1. web（チャット）モード
   - ボタン押下で定型テキストを `POST /api/chat/audio` に送り、返答音声（16kHz/mono/16-bit WAV）をストリーミング再生する
2. voice（音声対話）モード
   - Echo Base のマイク入力を WebSocket（`/ws/audio`）でホストへ送る（手動 PTT）
   - Moonshine による STT を経由して LLM と対話し、応答は Irodori-TTS で wav 化して再生する
3. relay（ブラウザ操作・リレー会話）モード
   - ホストに WebSocket で登録し、ホストから push された発話（`play`）を指定ペルソナの声色で再生する
   - ブラウザ UI から「AI 同士の会話（実機 2 台、または 1 台で 2 体）」「実機のキャラクターへの話しかけ」を操作する
4. recorder（録音再生）モード
   - ホスト・Wi-Fi 不要。録音をフラッシュ（LittleFS）に保存し、ダブルクリックで再生する
5. parrot（オウム返し）モード
   - ホスト・Wi-Fi 不要。音量で発話を検出して自動録音し、再生サンプルレートを変えた声で言い返す
6. timer（タイマー）モード
   - ホスト・Wi-Fi 不要。1〜25 分のタイマー。残り時間を LED で示し、残り 1 分と時間切れを声で知らせる

### 3.3 推奨アーキテクチャ

1. AtomS3-Lite が入力イベントを受ける
2. バックエンドへテキストまたは音声を送信する
3. バックエンドが OpenAI API 互換で LLM と通信する
4. 応答テキストを Irodori-TTS サービスへ渡す
5. 生成音声を wav としてデバイスへ返す
6. Echo Base のスピーカーから再生する

### 3.4 接続方式の採用方針

音声対話時に AtomS3-Lite と Irodori-TTS / Moonshine 実行ホストをどう接続するかについては、Wi-Fi を主経路として採用する。

採用理由は以下の通り。

- web モードの HTTP 通信と同じ経路を流用できる
- AtomS3-Lite は Wi-Fi 通信を前提にした設計と親和性が高い
- AtomS3-Lite を Bluetooth オーディオデバイスとして実装するより構成が単純である
- 音声データ、制御命令、状態取得を同一 API に統合できる
- 将来的に WebSocket や chunked transfer による低遅延ストリーミングへ拡張しやすい

Bluetooth を主経路にしない理由は以下の通り。

- Bluetooth オーディオ接続では、AtomS3-Lite 側にオーディオ周辺機器プロファイル相当の実装負荷が発生する
- マイク入力とスピーカー出力を 1 台の外部ホスト向け音声デバイスとして安定運用する難易度が高い
- 制御用の通信経路を別途持つ必要があり、システムが二重化しやすい
- そもそも AtomS3-Lite の ESP32-S3 は Bluetooth Classic 非対応で、A2DP（Bluetooth オーディオ）を使えない
- 接続管理、再接続、ペアリング、音声経路切替の複雑度が上がる

したがって、標準構成は以下とする。

- AtomS3-Lite とホストは Wi-Fi で接続する
- AtomS3-Lite は音声入出力の終端として動作する
- ホストは STT、LLM、TTS の実行主体として動作する
- AtomS3-Lite は PCM または wav ベースの音声データと制御情報を送受信する

Bluetooth の扱いは補助用途に限定する。

- 初期設定用の補助チャネル
- 将来の簡易リモコン的な制御チャネル

音声の主経路としては採用しない。

### 3.5 Web 操作の構成

当初は AtomS3-Lite 自身が Web サーバーになる案も検討したが、メモリ制約（PSRAM なし）と実装負荷から
**ホストが静的ファイル（`frontend/`）を `/frontend` で配信し、ホスト API を呼ぶ構成**を採用した。

1. ブラウザは同一ネットワークからホストの `/frontend/` へアクセスする
2. フロントエンドはホスト API（`/api/devices`、`/api/conversation/*`、`/api/chat/audio` など）を呼ぶ
3. 実機への指示はホストが WebSocket（`/ws/audio`）で push する（デバイスは HTTP サーバーを持たない）

## 4. 対応範囲

### 4.1 初期フェーズ

- Wi-Fi 接続
- AtomS3-Lite 上のモード切替
- LLM へのテキスト問い合わせ
- テキスト応答の取得
- Irodori-TTS による wav 生成
- wav の受信と再生
- ブラウザ操作（ホスト配信の Web UI）
- エラー時の簡易リトライとユーザー通知

### 4.2 拡張フェーズ

実装済み:

- マイク入力による音声対話（Moonshine による STT）
- 音声再生の逐次ストリーム再生（WAV をチャンク受信しながら再生）
- 会話履歴管理（`device_id::session_id` 単位）
- 複数台のペルソナ・声色の出し分けと、ホスト統括のリレー会話（実機 1 台で 2 体の再生も可）
- モード切替の音声案内、単体動作のモード（録音再生・オウム返し・タイマー）

未実装:

- LLM 応答のストリーミング（逐次生成・逐次合成）
- ローカルウェイクワード、空気越しの自動会話（音響ループのターン制御）
- Bluetooth オーディオ（ESP32-S3 が Bluetooth Classic 非対応のため、このハードでは不可）

## 5. 機能要件

### 5.1 LLM 通信

- OpenAI API 互換のリクエスト形式を採用する
- chat completions 系または responses 系のいずれかを選択可能にする
- ベース URL、API キー、モデル名を設定可能にする
- タイムアウトとリトライ回数を設定可能にする

### 5.2 デバイス通信

- AtomS3-Lite とホスト間の主通信は Wi-Fi を利用する
- テキスト要求、音声要求、状態取得、再生命令を同一の通信基盤で扱う
- 制御系 API は HTTP ベースとする
- 音声対話の主経路は WebSocket ストリームを採用する
- WebSocket は低遅延な音声チャンク送信、逐次 STT 結果通知、途中状態通知に利用する
- AtomS3-Lite は音声データの収集、分割、送信、受信バッファ制御までを担当する
- AtomS3-Lite 上では STT、TTS、LLM の推論処理を行わない

### 5.3 音声合成

- TTS 入力は LLM の応答テキストを基本とする
- TTS エンジンは Irodori-TTS を採用する
- Irodori-TTS の実行環境は host マシン上の uv 管理環境を前提とする
- Irodori-TTS の配置先は third_party/irodori-tts を基準パスとする
- 初期対応フォーマットは wav とする
- mp4 は任意対応とし、サーバー側で wav へ変換できることを要件とする
- 再生前にサンプルレート、チャンネル数、ビット深度を検証する

### 5.4 音声認識

- マイク入力の STT エンジンは Moonshine を採用する
- Moonshine はライブ音声向けの低遅延処理を前提に利用する
- Moonshine のソース配置は third_party/moonshine を基準とする
- Moonshine の Python binding は host の uv 環境へローカル source dependency として導入する
- 音声入力は原則としてバックエンドまたは中継ホストで処理する
- 将来のストリーミング対話を見据え、逐次文字起こしの取り扱いを考慮する

### 5.5 音声再生

- Echo Base スピーカーで再生できること
- 長尺音声は全量保持ではなく、分割受信またはストリーミング再生を検討する
- 再生中断、再生失敗、通信切断時の状態遷移を持つこと

### 5.6 デバイス操作

- 物理操作は BtnA 1 つ。クリック（モードごとの操作）、長押し 1.2 秒（モード切替）、
  ダブルクリック（recorder の再生。判定窓 400ms）を使う
- LED により待機中、処理中、再生中、録音中、エラーを表現する
- モード切替時には LED と音声案内（未生成ならチャイム）の両方で現在モードを判別できること

### 5.7 Web 操作機能（ホスト配信）

- ホストはブラウザ UI を `/frontend` で配信すること
- ブラウザ UI は以下を操作対象とする
   - 画面でデモ: 2 体のペルソナの会話をブラウザで再生（実機不要）
   - 実機で会話: 2 体の会話を実機で再生。出力先は「各ペルソナの実機（2 台）」または「1 台で両方」
   - 実機に話しかける: 入力テキストに選んだペルソナが答え、指定の実機がその声色で再生
   - 会話の停止、バックエンド（LLM/TTS/STT）と接続中の実機の状態確認
- 同一ネットワーク内のアクセスを前提にし、LAN 内利用を基本とする

### 5.8 モード切替フィードバック

- モード移行時は音声案内（例「チャットモードですわ。」）を再生する。案内音声はホストの
  `scripts/generate_mode_prompts.py` で参照音声の声色から生成してファームに埋め込む（任意）。
  未生成の場合はモードごとに異なるチャイムを鳴らす
- LED 色でモードを識別可能にする
- フィードバックは再生中や通信中に競合しないよう状態遷移を定義する

| モード | 音（案内未生成時のチャイム） | LED（待機） |
| --- | --- | --- |
| web | 低音の 1 音 | 青 |
| voice | 短い 2 音（上昇） | 緑（録音中は点滅） |
| relay | 上昇 3 音 | シアン |
| recorder | 下降 2 音 | 白（録音中は赤点滅） |
| parrot | 高い短音 3 回 | 黄（録音中は点滅） |
| timer | 同じ高さの 2 音 | 紫（動作中は残り時間で緑→黄→赤、時間切れは赤白点滅） |
| 再生中 | － | マゼンタ |
| エラー | 低音の断続 3 回 | 赤 |

## 6. 非機能要件

- 初期応答開始時間の目標は 2 秒から 5 秒程度を目安とする
- 音声再生はノイズや途切れが目立たないこと
- API キーをデバイスに直書きしない構成を優先する
- 障害解析のため、バックエンドでリクエスト単位のログを取得できること
- 将来のモデル切り替えでファームウェア修正を最小化すること
- Web UI はモバイル端末からのアクセスでも最低限操作可能であること
- フロントエンド資産は AtomS3-Lite の Flash 容量制約を考慮して軽量に保つこと

## 7. 制約と前提

- AtomS3-Lite は高負荷な LLM 推論や重い音声デコード処理の実行主体にしない
- Echo Base の利用には I2S と必要な初期化手順を考慮する
- ネットワーク遅延と音声ファイルサイズが UX に直結する
- 長尺音声や高サンプルレート音声はメモリ圧迫要因になる
- Web UI をデバイス内配信する場合は Flash 容量と静的アセットサイズ制約が厳しい
- third_party 配下の submodule 初期化と uv sync をセットで実施する必要がある
- Bluetooth は補助用途には使えても、主音声経路としては採用しない前提で設計する

## 8. 推奨データフロー

### 8.1 テキスト入力ベースの初版

1. デバイスが定型メッセージまたは簡易入力を送信する
2. バックエンドが LLM 応答を取得する
3. バックエンドが Irodori-TTS を実行する
4. wav を返却する
5. デバイスが再生する

### 8.2 音声入力拡張版

1. デバイスがマイク入力を録音する
2. デバイスが音声データを WebSocket ストリームでホストへ送信する
3. バックエンドが Moonshine で STT を実行する
4. LLM が応答を生成する
5. Irodori-TTS が音声を生成する
6. デバイスが wav を受信して再生する

### 8.3 Web 操作モード

1. ユーザーがブラウザでデバイスの Web UI にアクセスする
2. フロントエンドが問い合わせ内容または操作命令を送信する
3. デバイスがバックエンドへ要求を中継する
4. バックエンドが LLM 応答と Irodori-TTS 音声を生成する
5. デバイスが再生し、同時に Web UI へ状態を返す

### 8.4 推奨通信シーケンス

1. AtomS3-Lite は Wi-Fi 接続後にホスト API の疎通確認を行う
2. 音声対話モードでは、録音チャンクを WebSocket でホストへ送る
3. ホストは Moonshine、LLM、Irodori-TTS を順に実行する
4. ホストは結果テキストと再生用 wav を AtomS3-Lite へ返す
5. AtomS3-Lite は再生と状態通知のみを行う

## 9. API 方針

### 9.1 LLM API

- OpenAI API 互換を前提とする
- 差し替え候補として OpenAI、OpenRouter、vLLM、LM Studio、Ollama の互換レイヤーを想定する

### 9.2 音声系バックエンド方針

- TTS は Irodori-TTS 呼び出しをバックエンド API の内部実装として扱う
- STT は Moonshine 呼び出しをバックエンド API の内部実装として扱う
- デバイスは TTS と STT の内部差異を意識しない抽象 API のみを利用する

### 9.3 独自バックエンド API

デバイスからは以下のような API 群を利用する想定とする。以下は代表例であり、正本は [docs/backend-api.md](backend-api.md) とする。

- POST /api/chat（JSON 応答。Web UI / デバッグ用）
- POST /api/chat/audio（実機の主経路。生の audio/wav を返しヘッダ X-LLM-Text にテキストを載せる）
- POST /api/tts
- 音声ストリーム用に GET /ws/audio
- Web UI 配信用に GET /frontend
- デバイス状態取得用に GET /api/status
- 再生停止用に POST /api/playback/stop
- 状態確認用に GET /api/health

バックエンド内部では OpenAI API 互換の外部 API を呼び出す。TTS は常駐サイドカー
（不調時は infer.py の subprocess へフォールバック）で合成し、host/voices/reference.wav を
置くとその声色で合成する（話者リファレンス音声）。正本は [docs/backend-api.md](backend-api.md)。

詳細な入出力定義、イベント種別、WebSocket メッセージ形式は [docs/backend-api.md](backend-api.md) を正とする。

## 10. 初期開発順序

1. Echo Base の wav 再生だけを単独で安定化する
2. AtomS3-Lite のボタンによるモード切替と LED・効果音通知を実装する
3. AtomS3-Lite からバックエンドへテキスト送信する
4. OpenAI API 互換の LLM 応答取得を実装する
5. Irodori-TTS で wav を生成して返す
6. ブラウザ UI からの操作を実装する（ホスト配信）
7. その後に Moonshine と音声入力を追加する

詳細な実装順序、推奨スタック、ディレクトリ構成は [plans/implementation-plan.md](plans/implementation-plan.md) を正とする。

## 11. 成功条件

以下を満たせば初期マイルストーン達成とする。

- デバイスから 1 操作で問い合わせを開始できる
- ボタン操作でモード切替ができ、音と LED で判別できる
- LLM 応答を取得できる
- 応答テキストから生成された wav を再生できる
- Web UI から基本操作ができる
- 異常時にタイムアウトまたは失敗状態を検知できる

## 12. 開発運用方針

- AtomS3-Lite のファームウェアは PlatformIO ベースで管理する
- AtomS3-Lite へのソースコード書き込みは VS Code の PlatformIO 拡張機能経由で実行する
- firmware/atom/platformio.ini をファームウェア構成の正本とする
- Arduino IDE は検証用の参考に留め、主系の開発手段にはしない
